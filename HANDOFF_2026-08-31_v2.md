## 1. BLOCKER — the whole tree is CRLF-converted. Fix this before anything else.

v1 §6 says "4 files, all uncommitted." **That is wrong.** Actual `git status`:

```

```

Every tracked file — all `.py`, all `.md`, `frontend/index.html`, `.gitignore`,
`README.md`, both launchers — has been converted **LF → CRLF** in the working
tree. The committed blobs are LF. Nobody noticed, and v1 didn't record it.

Proof that only 4 files have real content changes:

```bash
git diff --numstat --ignore-cr-at-eol
# app/DEBUG_LOG.md, app/requirements.txt, start.bat, start.command
# -> 144 insertions, 1 deletion. Every other file: zero.
```

So: **4 files with real changes, 29 files of pure line-ending churn.**

### Why it matters

1. **`start.command` is now CRLF, which breaks the Mac launcher.** The shebang
   becomes `#!/usr/bin/env bash\r`, and macOS answers
   `env: bash\r: No such file or directory`. Double-click does nothing. This is
   the exact opposite of v1's claim that "Mac/Windows parity is preserved" — the
   yt-dlp fix inside that file is correct, but the file itself won't execute on Mac.
2. **Nothing is visibly broken on Windows**, which is why it went unnoticed.
   Python tolerates CRLF; `start.bat` wants CRLF anyway. Every test in v1 §5
   passed legitimately. This is a landmine, not a live failure.
3. Committing as-is buries the real 144-line fix inside a ~7,900-line diff and
   ships the Mac breakage to origin.

### When did it happen

Unknown — do not assume this session caused it. All commits are LF; the working
tree is CRLF. It may predate the yt-dlp work entirely (an editor with CRLF
defaults, or how this clone was originally copied). Treat it as pre-existing repo
hygiene debt that this session merely surfaced.

### Required fix, in this order

1. Add a `.gitattributes` at repo root:
   ```
   * text=auto
   *.command text eol=lf
   *.sh      text eol=lf
   *.bat     text eol=crlf
   *.cmd     text eol=crlf
   ```
   `*.command eol=lf` is the load-bearing line — it is what stops the Mac
   launcher from ever being re-broken.
2. Restore the 29 churn-only files so the diff is reviewable:

## 2. What the yt-dlp work actually changed (verified correct)

Four files, 144 lines. Classification of the original failure: **stale extractor**
— not bot-detection, not rate limiting, not IP quota.

| File | Change |
|---|---|
| `start.bat` | +11 — new section "2b. Keep yt-dlp current" |
| `start.command` | +14 — same block, bash form |
| `app/requirements.txt` | `yt-dlp>=2024.1.0` → `yt-dlp>=2026.8.19` |
| `app/DEBUG_LOG.md` | +118 — new Section 16 |

**Root cause:** both launchers run pip *only* when they create the venv
(`start.command:79`, and the matching `if not exist .venv\Scripts\python.exe` in
`start.bat`). With `requirements.txt` specifying a floor rather than a version,
yt-dlp froze at whatever shipped on first run, permanently. YouTube breaks stale
extractors within weeks. Symptom was `HTTP Error 403: Forbidden` after fallback
to the `ANDROID_VR` player client; upgrading to nightly fixed it with **no other
`ydl_opts` changes**.

The new block, inserted after venv resolution and before `main.py`:

```bash
.venv/bin/python -m pip install -U --pre -q \
    --disable-pip-version-check --timeout 10 --retries 1 \
    "yt-dlp[default]" \
  || echo "  (skipped — offline or PyPI unreachable; using installed version)"
```

**Design constraints — do not "simplify" these away:**

- Must live in the **launcher, not `main.py`** — upgrading after Python has
  imported `yt_dlp` means the current run still executes the old code.
- **`yt-dlp -U` does not work here.** Self-update only applies to the standalone
  binary; a pip install can only be updated by pip.
- **`--pre` (nightly) is the point** — YouTube extractor fixes land in nightly first.
- **Never block launch** — `--timeout 10 --retries 1` caps the offline penalty,
  `||` degrades failure to a warning.
- **Scoped to yt-dlp only.** Deliberately NOT `pip install -U -r requirements.txt`.
  `pyrekordbox` must not move silently — all the DB-write hygiene in `CLAUDE.md`
  (UUID, ArtistID/AlbumID, drag-import parity) is verified against the current one.
- Every-launch form chosen over a daily stamp file: measured cost ~1.4 s.

**Independently re-verified:** `2026.8.19` is a real **stable** release on PyPI
(currently the latest stable). So a fresh first-run `pip install -r
requirements.txt` — which does *not* pass `--pre` — can satisfy the new floor and
will not abort bootstrap on a clean machine. That was the one way this pin could
have bricked new installs; it doesn't.

**DEBUG_LOG numbering is correct:** §15 was taken earlier the same day by the
Traktor `SUBNODES` fix (committed as `3344145`), so this went in as **§16**, and
§16's header says so. §16.2 deliberately records the earlier wrong call
("transient throttling, wait 10–15 min") so it isn't repeated.

## 6. Found but deliberately NOT fixed

1. **Windows launcher window doesn't auto-close.** The watchdog raises SIGINT,
   which exits Python with code **2** on Windows; `start.bat` only treats `0`,
   `-1073741510`, `3221225786` as clean, so it prints "Server exited with error 2.
   Press any key to close." Server exits correctly and frees the port — cosmetic
   only. Blanket-treating 2 as clean would mask genuine errors; the better fix is
   an explicit `sys.exit(0)` on the watchdog path in `main.py`.
2. **`pyrekordbox>=0.3.0` is a floor, not a pin**, despite 0.4.4 being the verified
   version. Worth pinning exactly given how much DB-write behaviour depends on it.
   (Same class of bug as the yt-dlp one, still live.)
3. **No JS runtime installed.** node v24 is present but yt-dlp enables only deno by
   default. Enabling node did *not* fix the 403 and is unnecessary on current
   nightly. Installing deno is the more future-proof option if web-client
   extraction ever becomes mandatory.
4. Running `start.bat` from Git Bash prints `timeout: invalid time interval '/t'`
   (GNU `timeout` shadows Windows' `timeout.exe`). Test artifact, harmless.
